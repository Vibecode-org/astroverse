# Opt-in synthetic physical S-100k

Это искусственные стационарные центры, не наблюдения и не реальная сцена 100k.
Обычный `/` остаётся на пяти DE440s центрах. Запуск и runner —
[tests/README](../tests/README.md). Профиль, заранее объявленные бюджеты,
baseline и фактические измерения — [s100k_report.json](s100k_report.json).
Аппаратные 60+ fps, весь S-100k и массовый physical streaming остаются открыты.

## Профиль

Изолированный compose :5174 запускает `tests.s100k_provider`: 100000 записей
в SQLite, 100 секторов по 1000. Генератор пишет БД транзакцией; запрос читает
ограниченный сектор. Полный JSON-каталог не нужен. Реальный production API,
BSP, реестр пяти центров и supported UTC не меняются. Fixture явно маркирует
health, registry, positions и UI как synthetic. Старый 32×64 fixture независим.

Решётка 400×250: X=(column−199.5)×4000 km, Z=(row−124.5)×4000 km,
Y=0 ICRF/SSB. ID 50001 имеет тот же центр, что 50000: намеренное перекрытие,
никакого раздвигания. Векторы стационарны при любом поддержанном requested UTC;
каждый ответ содержит именно requested evaluated_at/JD TDB, новую дату нельзя
заменять старой. Это функция synthetic-модели, не эфемерида реальных тел.
Accuracy=null. Unknown не создаются специально ради счётчика.

При обычном открытии страницы fixture реестр включает opt-in бюджет и стартовый
обзор [0,8,24] render units с origin [0,0,0], взгляд к origin. Все 100000 центров
попадают в frustum при 1080p. Растровые диски перекрываются: число отправленных
точек/центров в frustum не означает 100000 различимых неперекрывающихся дисков.
Runner отдельно считает совпадения округлённых пиксельных центров.
`node tests/s100k_overlap.mjs` независимо считает номинальные круговые
пересечения по заявленному ракурсу: 1126913 пар, у всех 100000 есть сосед.
Это модель footprints по центрам Float32, не GPU raster occlusion.

## Существующий physical-путь

Используются те же `PhysicalApp`, `useVerifiedFrame`, `PhysicalSectorManager`,
`PhysicalScene`, Points/material/geometry и свободная камера. Второго viewer,
renderer или полного UI-списка 100k нет. Поиск по ID выполняет ограниченный SQL
query в реестре; выбор открывает обычную карточку, «Наблюдать» возвращает к телу.

Обычные лимиты manager 4096/128 строк в секторе сохраняются. Только профиль
получает 200000 resident+staging+in-flight строк (два временных набора), 64 MiB
serialized, 512 MiB decoded estimate, ответ ≤1 MiB; четыре worker и очередь
≤128 не меняются. Сектора сверяются по UTC/JD/revisions/identity до публикации.
Admission, drain отменённых worker, retry409/timeout и отказ без fallback прежние.
Новый секторный предел 1000 относится только к этому fixture, не production API.

Для >4096 строк слой готовит typed XYZ/color/level staging по 256 строк с
возвратом event loop. Порция имеет численный предел операций, не жёсткую
гарантию ms. До полного завершения staging не публикуется; новая заявка/dispose
инвалидирует подготовку. Ошибка очищает кадр. Validation ограничена сектором ≤1000 строк; глобальный merge и flat decode
порционные, с отменой. Prelude не фильтрует полный набор. Commit остаётся
синхронным; его время измеряется отдельно от elapsed подготовки.
Канонические центры остаются binary64. GPU данные не читаются как физика.

Commit заменяет содержимое буферов целиком, не renderer/material/Points. Рост
geometry до 131072 слотов освобождает старую geometry. Номинальные атрибуты
3670016 Б, staging ещё столько же; это не driver RAM и не полная JS-память.
На время rebase uniform линейно переносит действующий буфер одновременно с
камерой; новый завершённый буфер снова задан относительно актуального origin.
Picking/LOD используют ту же трансляцию. Момент карточки большого набора
обновляется после renderer.render, не по готовности только HTTP-кадра.

L0/L1 сохраняют центры: все загруженные известные точки участвуют в draw,
≤32 L1, ≤128 проверок LOD/RAF. Неизменённый level не отправляется каждый кадр.
Picking большого набора сначала проверяет AABB групп по 256 слотов с запасом
под экранный радиус, затем точные экранные расстояния и depth. Совпадение
расстояния/depth разрешает лексикографический ID, независимо от порядка загрузки.
Скрытые за другим маркером ID доступны через поиск. Shader log-depth сохранён.
L2, размеры физических моделей, поверхности и полный галактический диапазон
не входят в этот этап.

## Измерения и границы доказательств

Runner проверяет все identity и численные центры, настоящий WebGL
`renderer.info.render.points`, frustum, поиск/карточку границ секторов и пары
перекрытия, trusted yaw/pitch/roll/движение, rebase/выгрузку/возврат, даты,
Now/ускорение/реверс, partial failure и revision conflict. Снимки ресурсов
после прогрева проверяют renderer, geometry/textures и учтённые listeners.
Это не доказательство отсутствия любых JS/driver утечек. Manager decoded —
консервативная модель, не измеренный browser RSS. Память GPU-драйвера неизвестна.

Steady benchmark: 3s прогрев, 30s RAF timestamps, отдельно CPU camera/LOD.
Сборки и backend tests в этот период не запускаются. Сценарные frame-time
включают HTTP, UI и диагностическое чтение всего набора; это не чистый
изолированный benchmark движения. Apply sync и preparation/commit — разные
метрики, duration Promise нельзя выдавать за синхронный CPU apply.
Приборная точность RAF/Chrome округляет интервалы около 16.667 до 16.6/16.7 ms;
доля кадров ≤16.667 приводится буквально, без смены заранее заданного порога.
SwiftShader доказывает только функциональность. Аппаратный запуск фиксирует
реальный renderer, framebuffer/DPR, оборудование и ОС; headless RAF не GPU fence
и не измерение вывода на монитор.

При 100000 центров полный циклический обход LOD занимает до 782 RAF (~13 s при
60 Hz), выбранный центр повышается сразу. Это ограниченный L0/L1, не принятая
общая стратегия массового LOD. Центры не скрываются в ожидании обхода.

Для большого набора continuous coalescing ждёт acknowledgement завершённого
render прежде следующего запроса: HTTP не должен бесконечно отменять медленный
staging. Последнее желаемое время сохраняется, explicit controls по-прежнему
отменяют старый контекст. MCP проверяет прогресс displayedAt и знак времени;
стационарности synthetic координат для проверки Now недостаточно.


## Динамический update: 2026-11-12

Новый runner `browser_s100k_dynamic_mcp.py` отделяет измеряемые окна от полных
identity/numeric/frustum probes. Baseline до изменений сохранён отдельно;
`dynamic_update_stage` в основном JSON связывает исходные bundles, промежуточный
аппаратный прогон и окончательные измерения. Старые `measurements` не являются
доказательствами для нового кода. Чистые окна используют bounded sample buffers;
полные проверки идут после остановки записи метрик. Накладные расходы измерены
micro-loop отдельно, это нижняя оценка, не вычитание из результата.

Map identities/slots и AABB picking готовятся в staging. LOD/picking до commit
обслуживают предыдущий целый буфер. Отмена освобождает ссылки после drain;
частичный набор не публикуется. Typed bitmap заменяет Set занятых слотов;
плоские координаты сразу записываются в Float32, с отдельным вычитанием малых
offsets. Memory/admission/worker limits и численные допуски прежние.
`physicalFrameAsync` не расширяет 4096-body hierarchy contract.

Аппаратный renderer доступен (Apple M1 Pro / ANGLE Metal), но это headless
RAF, не монитор. В первоначальном прогоне строгий frame p95 16.667 ms сохранялся буквально, даже когда
Chrome выдаёт 16.7/16.8 ms. Динамические паузы и превышения budget остаются
FAIL, а не средним fps. Следующий ограниченный шаг — профиль allocations/GC и
пиков decode/staging при continuous time; без L2/поверхностей/новых источников.

## Текущий порог приёмки (решение пользователя2026-11-12)

Frame p95 ≤16.8ms принят пользователем. Прежние исходные измерения и порог
16.667ms сохранены как история; новое решение не меняет данные прогонов.
Сравнение допускает только1e-6ms на IEEE subtraction noise возле16.8ms,
не округление реальных превышений. Все другие CPU/p99/pause/memory/precision
бюджеты прежние. Это приёмка synthetic headless RAF на конкретном GPU,
не доказательство monitor presentation, реального S-100k или всей Фазы8.
Дополнительный runner поддерживает12 отдельных стресс-циклов с численными
проверками полного набора и ресурсов после каждого измеряемого окна.
