# Пространственный индекс и backend снимков — Фазы 3.0–3.2

`data/sectors.py` строит отдельный SQLite-артефакт из проверенного каталога.
Офлайн-разбиение подключено к backend через `DiskCatalog`. Новое HTTP API
ограничивает выборки и страницы; новый frontend читает снимки только для карточек, а подтверждённые
положения пяти тел — через отдельный `positions/1`. Legacy-режим сохраняет v2.

## Запуск

Из корня репозитория, Python 3.10+ со встроенным SQLite R-tree, без новых пакетов:

```bash
python3 -m data.sectors data/catalog_seed.json data/sectors.sqlite

# Если нагрузочный каталог ещё не создан:
python3 data/gen_catalog_100k.py
python3 -m data.sectors data/objects_100k.json data/sectors_100k.sqlite
```

В контейнере (сборка образа включает этот модуль):

```bash
docker compose run --rm --no-deps -w /app backend \
  python -m data.sectors data/catalog_seed.json /tmp/sectors.sqlite
```

Контейнерный пример проверяет сборку; `/tmp` удаляется вместе с контейнером.
Результат на хосте создавайте первой командой. Артефакты `data/sectors*.sqlite`
исключены из Git и Docker build context. Источник никогда не заменяется CLI;
выходной файл должен иметь расширение `.sqlite`.

Настройки: `--cell-size-ly` (32 по умолчанию), `--max-objects` (4096).
Сборка атомарна: при ошибке прежний индекс остаётся пригодным для чтения.

## Контракт координат и разбиения

Snapshot-семантика/оси/единицы/null/at422 — [COORDINATES](COORDINATES.md).
Индекс не подтверждает реальные центры на дату, frames не смешивает и не
преобразует. Render-координаты камеры нельзя передавать как координаты индекса.

- Звезда, планеты и дальнейшие потомки `parent` — неделимая группа. Её
  сектор определяется позицией корня; орбитальное движение не меняет сектор.
  Семейства с разными `scale` отклоняются, а не разрываются.
- Солнечная система хранится в отдельной группе `solar:system`.
- Семейства без полной позиции корня — в `<scale>:unlocated`, с границами
  `null`. Они сохраняются для поиска/карточек и не попадают в пространственные
  запросы. Положение не выводится из координат дочернего тела.
- Базовая сетка имеет фиксированный шаг. Плотные ячейки делятся октодеревом,
  до 16 уровней по умолчанию. ID: `<scale>:<frame>:ix:iy:iz[/octant…]`.
  При неизменной конфигурации ID не зависит от порядка входных объектов.
- Порог числа объектов мягкий: неделимая большая система, совпадающие корни
  на максимальной глубине и группы без позиции могут превышать его.
- Защита численных границ: координаты/границы ограничены `3e38` ly для
  float32 R-tree. Размер ячейки не должен вызывать underflow при делении
  на `2^max_depth`; отношение координаты к размеру — не более `2^52`.
  Непредставимые конфигурации отклоняются через `ValueError`. Границы листа
  консервативно включают корни даже при погрешности округления сетки.

## Хранение и чтение

SQLite содержит метаданные версии, таблицу секторов, R-tree их границ и
полные JSON-карточки объектов с индексами по ID и сектору. Ревизия сектора —
SHA-256 его контракта, границ и содержимого в стабильном порядке. Изменение
карточки не меняет ревизии независимых секторов. Изменение плотности может
разделить/объединить листья соответствующей ячейки и поменять их ID.

```python
from data.sectors import SectorIndex

index = SectorIndex("data/sectors.sqlite")
nearby = index.nearby("local", "equatorial", center=(0, 0, 0), radius=32)
sector_id = index.locate("earth")
solar_objects = index.objects(sector_id)
```

`nearby` выбирает листья по пересечению сферы и куба, а не проверяет видимость
каждого тела. R-tree даёт консервативных кандидатов; окончательная проверка
использует исходные float64-границы. Запрос никогда не смешивает frames или
масштабы. Границы считаются замкнутыми для запросов, поэтому на общей грани
могут вернуться оба соседа; сами объекты хранятся ровно в одном секторе.

`objects` читает только один лист, `locate` возвращает его ID или `None`.
Для неизвестного сектора `objects` поднимает `KeyError`. Полный `sectors()`
предназначен для офлайн-инспекции и не выставлен в HTTP. Обычный `SectorIndex`
следует переоткрывать после замены файла. Backend использует отдельную read-only
транзакцию `DiskCatalog.snapshot()` на запрос, включая всё время передачи
legacy-потока: метаданные, карточки и бинарные секции относятся к одному inode.
Атомарная замена пути не меняет уже открытый ответ.

## HTTP `spatial/1`

| GET | Результат |
|---|---|
| `/api/spatial/v1/contract` | Контракт `coordinates/1`, ограничения времени |
| `/api/spatial/v1/nearby?scale=local&frame=equatorial&x=0&y=0&z=0&radius=32` | Пересекаемые листья и ревизия `snapshot` |
| `/api/spatial/v1/sectors/{id}?limit=512&after={object_id}` | Страница карточек и их контрактов; `next_after` либо `null` |
| `/api/spatial/v1/objects/{id}/sector` | Сектор семейства и статус координат самого объекта |

`nearby`: только `local`/`galaxy`, `equatorial`/`galactic`, конечные центры
в диапазоне ±1e12 ly, радиус 0…1e6 ly. `limit` 1…128, по умолчанию 128;
если сфера затрагивает больше листьев — **413**, а не молчаливое усечение.
Это отбор bounding boxes корней, не точный список тел внутри сферы и не frustum.
Solar и unlocated доступны по ID, но не через nearby.

Страница сектора — 1…512 объектов; `after` до 512 символов. Порядок — ID,
курсор эксклюзивный. Полный лист не загружается ради страницы; даже неделимое
семейство больше 4096 объектов можно читать частями. Замкнутость семейства
гарантируется всему листу, не отдельной странице. Максимальный сериализованный
ответ — **2 MiB**; превышение — 413 с предложением уменьшить `limit`.
Поэтому один слишком большой объект нельзя получить этим маршрутом.
Для `next_after` проверяется только наличие следующего ID в той же транзакции;
его карточка не читается и не входит в байтовый бюджет текущей страницы.
Большая следующая карточка не блокирует получение предыдущей страницы.

`snapshot` опционален на всех маршрутах чтения данных. Клиент передаёт значение
из nearby при чтении страниц/ID; если артефакт изменился, возвращается
**409 `snapshot_changed` до проверки ETag**. Следует начать выборку заново.
Без этого параметра каждый запрос получает последний согласованный снимок.
Страница сектора передаёт текущую общую ревизию в `X-Catalog-Snapshot`
(включая 304), чтобы можно было начать согласованную пагинацию и без nearby.
Курсор без `snapshot` не обещает согласованность между публикациями.
Неизвестные ID/секторы дают 404; неверные параметры/frames/время — 422.
Недоступный/несовместимый опубликованный SQLite до начала ответа даёт 503,
`Retry-After: 1` и `Cache-Control: no-store`.
ID листа может содержать `/` октодерева; маршрут сектора поддерживает такой путь.

Ревизия листа — SHA-256 схемы, контракта координат, ID, границ и отсортированных
полных карточек. Его ETag дополнительно включает версию ответа, `limit` и
`after`. Независимое изменение другого листа не инвалидирует этот ETag.
Общая ревизия снимка включает схему, контракт, настройки разбиения и карточки
в исходном порядке. Nearby/locate валидируются общей ревизией. Weak, strong,
список и `*` поддерживаются; 304 не содержит тела. Cache-Control требует
ревалидации. Переходы split/merge и перенос семейства проверены тестами.
При отсутствии готового ответа в кэше ограничения выборки и размера ответа
проверяются до `If-None-Match`, включая `*`: запрос, превышающий лимиты,
сохраняет 413. Валидный кэшированный ответ может дать 304 без повторного
чтения карточек и сериализации.

`ASTROVERSE_SECTOR_CACHE_BYTES` задаёт бюджет LRU, по умолчанию **8 MiB**.
Считаются сериализованные bytes, размер представления ключа и резерв 256 байт
на запись; это бюджет кэша, не жёсткий предел RSS процесса. Слишком большая
запись не кэшируется, замена ключа учитывается один раз. Чтение освежает LRU,
потоки защищены lock. Старые ревизии могут оставаться до вытеснения, но никогда
не используются для новых ответов.

## Runtime и совместимость

SQLite schema **2** содержит карточки, исходный ordinal, поисковый текст,
индексы ID/сектора/scale и заранее построенные legacy v1/v2 BLOB.
`backend.prepare_runtime` запускается отдельным процессом при отсутствии,
смене входного файла или контракта. Выход — `*.runtime.sqlite`, либо
`ASTROVERSE_SECTOR_PATH`. Построение атомарно; сбой сохраняет предыдущий файл
и не разрешает запуск с устаревшими входными данными.

Производственный `CATALOG` — `DiskCatalog`, не список dict. Поиск использует
сохранённый lowercase текст и SQL `instr`, включая кириллицу; это дисковый
substring scan, не полнотекстовый inverted index. Возвращается до 500 компактных
строк; неизвестные позиции остаются доступны в поиске/карточках.
В памяти runtime нет полного `by_id`/haystacks. Подмена `CATALOG` списком
сохранена для существующих тестов/встраивания.

Полные legacy JSON/v1/v2 остаются доступны: JSON передаётся порциями около
64 KiB, бинарь читается через SQLite blobopen по 64 KiB. Исходный порядок и
wire v1/v2 сохранены; identity binary сохраняет Content-Length, nginx gzip —
прежний weak ETag/Vary. Полная legacy-выдача по-прежнему растёт с каталогом
по трафику, но не требует полного списка Python в worker.

Фильтрованные legacy-ответы сохраняют прежний формат в пределах **4096
объектов / 8 MiB**; превышение явно даёт 413 с направлением в spatial API.
Их LRU — отдельные 8 MiB (`ASTROVERSE_BINARY_CACHE_BYTES`), ключ содержит
ревизию каталога и формат/фильтры. Legacy v2 остаётся render-форматом;
новый spatial API возвращает JSON с явной семантикой, не «физический v2».

## Потоковая сборка и ограниченные обновления (2026-11-06)

Производственный `backend.prepare_runtime` теперь использует
`data.streaming_catalog.build_streaming_index`, а не `load_catalog` полного
списка. JSON читается по объекту через ijson; граф parent, семьи, очереди
разбиения и сортировки хранятся в SQLite с 8 MiB page cache и `temp_store=FILE`.
Связность, циклы, дубликаты, cross-scale семьи и все локальные поля проверяются
до публикации. Неизвестные положения сохраняются как прежде.

`data.streaming_binary` пишет бинарные секции во временные файловые потоки,
интернирует строки в SQLite и копирует в BLOB по 64 KiB. Полный словарь строк,
ID→индекс и большие SoA-массивы больше не нужны в RAM сборщика. На seed
проверено байтовое совпадение v1/v2 и совпадение всех ревизий с эталонным
списочным writer из `data/sectors.py`; он остаётся для тестов/малых явных списков.

```bash
docker compose run --rm --no-deps -w /app backend \
  python -m backend.prepare_runtime data/catalog_seed.json /tmp/runtime.sqlite
```

Локальный административный интерфейс обновления (не публичный HTTP writer):

```python
from data.incremental_catalog import publish_changes
metadata = publish_changes(path, expected_revision=previous_revision,
                           upserts=changed_cards, deletes=removed_ids)
```

Патч ограничен 4096 upserts и 4096 deletes, суммарно 8 MiB. Локальная проверка
и SQL-граф отклоняют сирот, циклы и конфликтующие операции. Advisory lock
сериализует сотрудничающих writers; сравнение глобальной ревизии отклоняет
устаревший патч. Lock inode сохраняется намеренно. Публикация — atomic rename;
старые read-транзакции продолжают читать прежнюю версию.

Разбиение пересчитывает позицию всего parent-семейства. Совпавшие ревизии
листов переиспользуют прежние object/search rows; независимые ETag не меняются.
`reused_sectors` и `parent_revision` доступны в метаданных. Сигнатура исходного
JSON сохраняется: при неизменном базовом источнике патч переживает рестарт;
явная новая версия исходного JSON снова является источником полной сборки.

Это **ограниченный патч с переиспользованием секторов**, а не O(изменений)
публикация: граф/разбиение и совместимые полные v1/v2 всё ещё требуют линейного
прохода и создания нового SQLite. Пиковое место на диске включает старый
артефакт, staging, секции и VACUUM. Сбой не заменяет прежнюю публикацию.
Онлайн-сборщик исходного NASA-каталога также пока собирает Python-списки;
новый ограниченный путь начинается с подготовленного JSON, а не с HTTP ingestion.

Физический `positions/1` использует отдельный динамический сектор только
для пяти центров. Его frame/время не смешиваются со снимками и камерой
legacy-v2. Клиентский snapshot-кэш хранит только сериализованные страницы,
оценивает 2 байта на UTF-16 code unit + overhead, ограничен 4 MiB и 4096
декодированными карточками одного запроса. 409 очищает кэш и разрешает один
повтор locate; 304 использует только существующую страницу.
