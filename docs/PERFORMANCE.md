# Производительность: измерения до/после (Фазы 1–2)

Все замеры сделаны на каталоге 100 000 синтетических объектов (`data/gen_catalog_100k.py`), viewport 1440×1000, headed Chrome (Apple M1 Pro, WebGL2 через ANGLE/Metal), стек на `http://localhost:5173`. FPS замеряется через rAF 3 секунды после прогрева; числа ниже — медиана трёх прогонов, если не указано иное.

## До оптимизаций (базовая линия)

| Метрика | Значение |
|---------|----------|
| Draw call (`renderer.info.render.calls`) | 245 |
| Треугольники | 35 476 706 |
| FPS (headed) | 11.8 |
| Heap (used JS heap) | ~245 МБ |
| LOD-уровни | [60 722 / 39 150 / 128] |
| `/api/objects` JSON (gzip) | 3.33 МБ |
| Бинар v2 | не было |

Источник: ROADMAP.md, секция Фаза 1; замер «до» до изменений LOD.

## После оптимизаций (100k, текущее состояние)

| Метрика | Значение | Изменение |
|---------|----------|-----------|
| Draw call | 44 | 245 → 44 (< 50 цель ✓) |
| Треугольники | 4 083 240 | 35.5 М → 4.1 М (×8.7 меньше) |
| FPS (headed, анимация) | **~39** (39.0 / 39.3 / 40.0) | 11.8 → ~39 (цель 30+ ✓) |
| FPS (headed, на паузе) | **~46** (42.9 / 46.7 / 46.8) | — |
| Heap (used JS heap) | ~252–268 МБ | ~245 МБ (без роста) |
| LOD-уровни | [43 547 / 56 433 / 20] | L2 бюджет 128 → 20 |
| Бинар v2 (100k, распакованный) | 13 000 172 Б | 130 байт/объект (< 20 МБ ✓) |
| Бинар v2 по сети (gzip, level 5) | 2 456 590 Б | 5.3× меньше, 18.9 % от raw |
| Полный JSON по сети (gzip) | 3 331 810 Б | v2+gzip в 1.36× меньше |
| v2 парсинг (binary-parse) | **~129 мс** (122–164) | было ~135–166 мс |
| Каталог загрузки (catalog-load) | **~180 мс** (172–368) | было ~280–347 мс |
| `/api/search` (warm, 100k) | **7–10 мс** на сервере, ~11.5 мс по HTTP | было ~124–129 мс |

Точное распределение LOD-уровней зависит от положения камеры; важен итог: сумма уровней равна числу объектов, L2 ограничен бюджетом 20.

## Что изменилось

### L1-сферы уменьшены (`lodInstanced.js`)
- Stars: 8×6 → 96 треугольников (было больше)
- Остальные (планеты и т.д.): 6×4 → 48 треугольников
- L2_BUDGET снижен с 128 до 20 (`lodController.js`)

### LOD: подсказки позиций (`lodController.js`)
- Плейсхолдеры — прямые дети группы, матрица мира единичная; позиции читаются напрямую, без `getWorldPosition` (экономим 200k Map-поисков/кадр на 100k)
- Плейсхолдеры скрыты (`visible = false`) за исключением момента crossfade L2 — рендерер не обходит 100k пустых `Object3D` каждый кадр
- `Math.hypot` в горячих циклах заменён на `Math.sqrt` (hypot ≈5× медленнее): циклы проекции и пикинга выполняются на каждый объект каждый кадр
- Статичным объектам (`!obj.parent`) больше не вызывается `setPosition`: их позиция в L0-облаке засеяна один раз, перезаливка буфера на 100k — ~720 КБ/кадр впустую

### Анимация: нет пересчёта орбит на паузе (`animation.js`)
- Орбитальные углы и вращения пересчитываются только при изменении `simTime`
- Экзопланеты двигаются по плоскому орбитальному базису (`orbit.basis`, 6 чисел из `buildDeepSky`) с инлайн-математикой вместо `Vector3`-цепочек и `placeOnOrbit`: на 100k это ~39k итераций за кадр
- `placeOnOrbit` остался fallback для объектов без заранее посчитанного базиса
- Фотонное кольцо чёрной дыры всё ещё разворачивается к камере каждый кадр

### `scaleCatalog`: кэш производного массива (`buildSolarSystem.js`)
- `displayRadius`/`scale` считаются один раз на пару (массив каталога, режим масштаба)
- Кэш — `WeakMap` по массиву каталога, поэтому повторный монтаж сцены (StrictMode, восстановление после ошибки) не клонирует 100k объектов заново
- Память — примерно размер каталога; освобождается вместе с массивом

### Бинарный каталог v2 (`catalog.py`, `readBinaryCatalog.js`, `app.js`)
- Полный каталог грузится как 13 МБ бинар вместо полного JSON
- Строки (`id`/`name`/`latin`) декодируются одним проходом `TextDecoder` по всей секции `strings`; раньше было 300k отдельных вызовов на 100k объектов. Подробности и компромисс по памяти — в [BINARY_CATALOG.md](BINARY_CATALOG.md#декодирование-строк-на-фронтенде)
- На 3 471 объекте parse — ~4.2 мс, catalog-load — ~18 мс (медиана 5 перезагрузок)

### Транспорт: gzip для `application/octet-stream` (`frontend/nginx.conf`)
- `gzip_types` дополнен `application/octet-stream`, включён `gzip_vary on`
- 100k: 13 000 172 Б → **2 456 590 Б** по сети (5.3×, level 5, ~150–200 мс CPU на ответ)
- 3 471: 319 979 Б → **83 783 Б** (3.8×)
- Для сравнения полный JSON на 100k по сети — 3 331 810 Б, то есть v2+gzip выигрывает
  ещё и по трафику (не только по парсингу)
- Важно: gzip не уменьшает ни память после распаковки, ни время парсинга —
  только сеть. Критерий «1 млн ≈ 30 МБ» он не закрывает (см. ROADMAP, Фаза 2)
- Побочный эффект: nginx отдаёт сжатый ответ chunked, без `Content-Length`;
  тесты поэтому проверяют `Content-Encoding` и распакованное тело, а не длину

### Кэш на клиенте: ETag + `Cache-Control` (`backend/app.py`)
- Каждый ответ `/api/objects` (JSON, v1, v2 binary) получает `ETag`, `Cache-Control: public, max-age=0, must-revalidate` и `Vary: Accept`
- ETag собирается из ревизии файла каталога (`size-mtime_ns`), версии формата и фильтров (`q`, `kind`, `scale`); запрос с `If-None-Match` возвращает `304` без тела
- Перезагрузка страницы на 100k — ~2 мс и 0 байт каталога вместо повторной передачи 2.46 МБ; именно это дало падение `catalog-load` с ~280–347 до ~180 мс на тёплом кэше
- nginx ослабляет ETag до `W/"…"` у gzip-ответов, поэтому сравнение принимает weak-валидаторы и списки через запятую (см. AGENTS.md)

### Индекс каталога (`backend/app.py`)
- `catalog_index()` один раз строит `id → объект` и по одному lowercase-блоку на объект (6 полей через `\n`)
- `/api/search` и `?q=` на `/api/objects` больше не делают 6 `str().lower()` на объект при каждом запросе
- `/api/objects/{id}` — O(1) вместо линейного поиска
- 100k: поиск 124–129 мс → **7–10 мс** (×13–17), построение индекса 157 мс однократно, ~93 Б/объект
- Индекс перестраивается по идентичности списка `CATALOG` (тесты подменяют список), а не по мутации на месте

## Критерии приёмки (из ROADMAP)

| Критерий | Результат | Статус |
|----------|-----------|--------|
| 100 000 объектов стабильно при 30+ fps | ~39 fps | ✓ |
| Draw call < 50 | 44 | ✓ |
| Объекты проявляются плавно (L1↔L2 crossfade) | Есть | ✓ |
| Нет визуальной регрессии solar/local/galaxy | 20 smoke-тестов | ✓ |
| Нет утечек геометрий/материалов/текстур | smoke_binary: ресурсы не растут | ✓ |
| Повторная загрузка не тянет каталог заново | 304, 0 байт, ~2 мс | ✓ |

## Как замерить самостоятельно

```bash
# 100k стек
python3 data/gen_catalog_100k.py
docker compose -f docker-compose.yml -f docker-compose.100k.yml up --build -d

# Открыть http://localhost:5173 в headed Chrome (Apple M1 Pro / аппаратный GPU)
# В DevTools MCP: установить probe из tests/browser_smoke/common.py
#   (INSTALL_PROBE), переключиться в «Окрестности Солнца» и 3 секунды считать
#   кадры через requestAnimationFrame.
# Метрики: window.__astroverseSmoke().metrics (calls/triangles/points),
#   .lodCounts, .resources; heap — performance.memory.usedJSHeapSize.
# Для 100k: pytest tests/browser_smoke/ -m stack100k -v
#   (headless проверяет бюджеты draw call/треугольников, но не fps:
#    SwiftShader на 100k рисует ~0.5 кадра/с).

# Транспорт: размер по сети и распакованный размер
curl -s -o /dev/null -D- -H 'Accept-Encoding: gzip' \
  'http://localhost:5173/api/objects?format=v2'   # Content-Encoding: gzip, chunked
curl -s -o /dev/null -D- -H 'Accept-Encoding: identity' \
  'http://localhost:5173/api/objects?format=v2'   # Content-Length: 13000172
curl -s -o /dev/null -w '%{size_download}\n' -H 'Accept-Encoding: gzip' \
  'http://localhost:5173/api/objects?format=v2'   # 2456590

# Кэш: ETag и условный запрос
ET=$(curl -s -o /dev/null -D- 'http://localhost:5173/api/objects?format=v2' \
  | awk -F': ' 'tolower($1)=="etag"{print $2}' | tr -d '\r')
curl -s -o /dev/null -w '%{http_code} %{size_download}\n' \
  -H "If-None-Match: $ET" 'http://localhost:5173/api/objects?format=v2'  # 304 0
```
