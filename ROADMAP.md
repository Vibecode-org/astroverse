# ROADMAP — путь к SpaceEngine-подобному планетарию

> Рабочий документ. Отмечаем выполненное, пишем комментарии прямо здесь.
> Обновлять по мере завершения шагов, а не «в конце спринта».
>
> Легенда статусов: `[ ]` не начато · `[~]` в работе · `[x]` готово и проверено · `[!]` заблокировано

**Цель:** локальный планетарий, который держит **1 000 000+ объектов** и
подгружает их по мере приближения, с качественной графикой горячих объектов.

**Текущее состояние (2026-09-28):** 3 471 объект, плоский список, каждый объект —
отдельный меш, созданный при старте сцены. Всё грузится в память сразу.

---

## 0. Ограничения, которые нельзя нарушать

Это не «хотелки», а условия, при которых проект останется рабочим.

| # | Ограничение | Почему |
|---|---|---|
| K-1 | **Никаких мешей на каждый объект.** Только `Points`, `InstancedMesh` или единичные детальные меши | 1 млн объектов × 1 draw call = неработающий WebGL. Целевой бюджет — единицы десятков draw call на кадр |
| K-2 | **Данные в типизированных массивах, структура массивов (SoA)** | JSON 600 байт/объект × 1 млн = 600 МБ. Целевой размер — 24–40 байт/объект |
| K-3 | **Масштаб отображения задаётся во фронтенде, физика — в данных** | Каталог хранит реальные величины, сжатие масштабов — визуальная задача. Уже так сделано для `getSolarDistance` / `getMoonOrbitDistance` |
| K-4 | **Данные, которых нет, остаются `null`. Ничего не синтезировать** | Принцип из `build_catalog.py`. Астрономия должна оставаться проверяемой |
| K-5 | **Никаких `Math.random()` там, где результат должен быть воспроизводим** | Позиции объектов, орбиты и псевдослучайные текстуры кешируются — нужен детерминизм от id |
| K-6 | **Никаких глобальных модулей-синглтонов с изменяемым состоянием** | Кеши ресурсов уже есть в `bodies/resources.js`; состояние сцены — только в `appRef` |
| K-7 | **Проверка изменений измерима** | Для рендера — скриншот и счётчики draw call; для данных — тесты `unittest` |

## Фаза 0 — Орбиты экзопланет `[x]`

### Проблема

У всех **1 500 из 1 500** экзопланет `ra`, `dec`, `distance_ly` совпадают со
звездой-хозяином (NASA отдаёт системную астрометрию). Звезда `radius=0.35`,
планета `0.16` → **планета геометрически внутри меша звезды**. Из 2 733 объектов
масштаба `local` только **1 233 уникальные позиции**. При выборе планеты камера
встаёт на позицию звезды, и пользователь видит звезду вместо планеты.

### Шаги

- [x] **0.1** Подтвердить диагноз на данных (1500/1500 совпадений ra/dec/distance)
- [x] **0.2** Орбитальная математика в `bodies/helpers/orbitHelpers.js`:
      `hashUnit`, `orbitFrame`, `orbitPhase`, `getLocalOrbitRadius`, `placeOnOrbit`
- [x] **0.3** Двухпроходное построение локальной сцены в `useThree.js`
- [x] **0.4** Анимация орбит в `animate()` от `state.simTime`
- [x] **0.5** Скриншот-проверка: экзопланета видна отдельно от звезды-хозяина
- [x] **0.6** Численная проверка на реальном каталоге (стенд `verify.mjs`)
- [x] **0.7** Свет: один `PointLight` у хозяина отслеживаемого объекта

### Критерии приёмки

- [x] Уникальных позиций среди объектов `local`: **2 733** (было 1 233)
- [x] Сирот без родителя: **0**
- [x] Выбор экзопланеты в списке показывает сам экзопланет
- [x] Пересечений «планета ↔ хозяин»: **0** (мин. дистанция 1.26 ед. при радиусе звезды 0.35)
- [x] Орбиты двигаются по `simDate` и корректно идут назад по времени
- [x] Нет ошибок в консоли, счётчики ресурсов не выросли
- [ ] ~~Нет пересечений между объектами~~ → **перенесено в Фазу 4**

### Комментарии

- *2026-09-28.* Диагноз подтверждён. Реальные орбитальные элементы (e, i, Ω, ω, M₀)
  в каталоге отсутствуют, поэтому орбиты круговые и детерминированные от id:
  физика не выдумывается (K-4), но и не выдаётся за реальную — это визуальное
  приближение, как уже сделано для поясов астероидов.
- *2026-09-28.* **Фаза неожиданно вскрыла второй баг.** Экзопланеты рендерились
  почти чёрными: в виде «окрестности Солнца» единственный источник —
  `AmbientLight` цвета `0x0e1322` (практически чёрный), а `sunLight` там выключен.
  Раньше это было незаметно, потому что планета пряталась внутри звезды. Решено
  одним `PointLight`, который встаёт в хозяина отслеживаемого объекта. Светить от
  каждой из тысяч звёзд нельзя, а фаза 1 всё равно потребует пересмотра освещения.
- *2026-09-28.* **Открыто: 53 пары пересекающихся объектов, и это не наша регрессия.**
  Например две разные звезды `hd_133131_a` и `hd_133131_b` стоят в 0.023 ед. друг
  от друга при радиусе 0.35. Обе — корневые объекты, которые ставятся только через
  `equatorialXYZ` (его фаза 0 не трогала). Причина — сжатие дистанций в
  `galaxy.js::equatorialXYZ`: при 1 233 системах разные системы попадают в одну
  точку. Это предвестник Фазы 1 и лечится Фазой 4.
- *2026-09-28.* Плоскость орбиты общая для системы, **фаза — своя у каждого тела**.
  Это неочевидно: если брать фазу от id системы, все планеты одной системы
  лягут в одну точку, потому что у них одинаковый `parent`.

## Фаза 1 — Трёхуровневый LOD-рендер `[ ]`

### Цель

Разделить рендер на три уровня детализации по расстоянию до камеры.
Основано на идее SpaceEngine: на больших дистанциях видны только крупные объекты,
по мере приближения к сектору проявляются всё более мелкие.

| Уровень | Когда | Чем рисуем | Draw call |
|---|---|---|---|
| **L0 far** | дальше порога | один `THREE.Points` на все объекты, атрибуты размера/цвета | 1 |
| **L1 mid** | средняя дистанция | `InstancedMesh` на вид (планета / звезда / скопление) | ~5–10 |
| **L2 near** | близко или выбран | индивидуальный детальный меш | единицы |

### Шаги

- [ ] **1.1** Зафиксировать метрику: `renderer.info.render.calls` и `triangles`
      до и после каждого шага. Добавить в стенд замеров
- [ ] **1.2** Определить пороги переключения по **экранному** размеру
      (видимый угловой радиус), а не по абсолютной дистанции — иначе переключение
      зависит от размера объекта и «дёргается»
- [ ] **1.3** L0: собрать `Points` из массива каталога, кастомный шейдер с
      `gl_PointSize` по расстоянию и пер-вершинным цветом
- [ ] **1.4** Перенести выбор объекта (пикинг) на raycast по `Points` с
      порогом в экранных координатах
- [ ] **1.5** L1: `InstancedMesh` на вид, пер-инстансные матрица и цвет
- [ ] **1.6** L2: поднимать детальный меш только для близких/выбранных объектов,
      остальные — placeholder
- [ ] **1.7** Гистерезис между уровнями (порог входа ≠ порога выхода),
      иначе объект мигает на границе
- [ ] **1.8** Плавное появление (fade по альфе) при приближении

### Критерии приёмки

- [ ] 100 000 объектов рендерятся стабильно при 30+ fps
- [ ] `renderer.info.render.calls` < 50 на любом кадре
- [ ] При подлёте объект плавно проявляется, без «щелчка»

## Фаза 2 — Бинарный формат каталога `[ ]`

### Проблема

Текущий каталог — ~600 байт на объект. 1 млн объектов = 600 МБ, такой ответ
нельзя отдать и нельзя распарсить в браузере.

### Формат

Structure-of-arrays, little-endian, версионированный заголовок.

| Массив | Тип | Байт/объект |
|---|---|---|
| `position` | 3 × `float32` | 12 |
| `size` | `float32` | 4 |
| `color` | `uint32` | 4 |
| `kind` | `uint8` | 1 |
| `flags` | `uint8` | 1 |
| `parentIndex` | `int32` | 4 |
| **Итого базовый** | | **~26–32** |

1 млн объектов ≈ **30 МБ** — грузится один раз, живёт в типизированных массивах.

### Шаги

- [ ] **2.1** Описать формат заголовка (magic, версия, счётчики массивов, словарь)
- [ ] **2.2** Экспортёр `data/export_binary.py` рядом с существующим сборщиком
- [ ] **2.3** Тест round-trip: бинарный → каталог совпадает с исходным
- [ ] **2.4** Загрузка через `fetch` + `arrayBuffer`, разбор в `DataView`
- [ ] **2.5** Сохранить детальный JSON для выбранного объекта (по id) — полные
      описания не нужны для всех 1 млн

### Критерии приёмки

- [ ] 1 млн объектов в бинарнике ≤ 40 МБ
- [ ] Round-trip тест проходит
- [ ] Выбор объекта по-прежнему отдаёт полную карточку
