## Цель и промежуточные рубежи

Долгосрочная цель — отразить все известные на дату обновления астрономические
тела, расширяя охват проверяемых источников и поддерживая актуальность каталога.
Это открытая цель развития: миллион записей и S-100k — проверочные рубежи,
а не верхний предел каталога и не доказательство полного охвата. Для каждого
источника/типа тел фиксировать дату, доступный и импортированный объём,
ограничения выборки и пробелы. Наличие карточки не подтверждает положение:
неизвестные параметры остаются null, физическая сцена требует проверенной модели.

**Целевая архитектура хранения (согласовано 2026-11-10):** все рабочие данные
о телах и моделях хранятся и обновляются в БД. Фиксированные JSON-файлы не служат
основным каталогом тел, полный `objects.json` для запуска не требуется. JSON
допустим для API, тестов и служебных файлов. Текущий seed/JSON startup — переходный
путь; его миграция и общий дисковый реестр ещё открыты.

v1.0: свободный полёт от галактики до поверхности, непрерывный масштаб,
качественная графика и честные астрономические данные. Критерии:

- [ ] Docker macOS/Linux без ручных шагов, LAN; воспроизводимость, тесты,
  актуальная документация, отсутствие ошибок консоли/регрессий.
- [ ] Найти → подлететь → облететь → поверхность → галактика без перезагрузки,
  дискретных переключений и необходимости читать инструкцию.
- [ ] Миллион записей в каталоге, ограниченная residency без полной стартовой загрузки.
- [ ] Штатные production startup/обновления/offline работают с проверенной БД,
  без фиксированного JSON-каталога тел и обязательного полного objects.json.
- [ ] Реальные положения выбранной даты/Now в заявленной точности;
  вращение/наклоны, эллиптические орбиты, эфемериды, реверс без дрейфа.
- [ ] 60+ fps / 1080p на Apple M1 / GTX 1060, <50 draw call; аппаратный GPU.
- [ ] Публичный HTTPS, защита/логи/health, проверенные обновление/откат/backup restore.

**Рубеж S-100k (уточнён пользователем 2026-11-10, до полного v1.0):**
при открытии frontend сцена отображает **100 000 объектов**, с каждым можно
взаимодействовать, сохраняя **60+ fps**. Число записей на сервере или только
2048 resident этот рубеж не закрывают. Сначала допускается явно synthetic
приёмка renderer/UI; реальная сцена принимается отдельно по подтверждённым
положениям, без подмены данных и искусственного раздвигания центров.
Проверять выбор/picking, поиск, карточку, refocus/наблюдение и время для любого
ID, включая перекрытия в проекции; замерять также загрузку и первый интерактивный
кадр. Фиксировать каталог/resident/submitted/видимый набор, LOD, сценарий и
оборудование, frame-time распределение/паузы, CPU/GPU/RAM и draw calls.
SwiftShader годится для функциональных проверок, но не принимает 60+ fps.
Воспроизводимый synthetic-профиль открывает эти 100k без ручной подстановки
в консоли; тестовые данные не попадают в обычный production-запуск.
Точный профиль нагрузки и бюджет старта фиксируются до аппаратного benchmark.

Вне v1.0: VR, моды, мультиплеер, полная процедурная вселенная, редактор планет.

## Обязательные ограничения

| ID | Требование |
|---|---|
| K-1 | Points/InstancedMesh и единичные детальные меши; не меш на строку |
| K-2 | Типизированные SoA, целевой core 24–40 Б/объект; это не full v2 |
| K-3 | Физика отдельно от камеры/GPU; линейный масштаб сохраняет центры/расстояния |
| K-4 | Нет данных — null; synthetic явно обозначен |
| K-5 | Воспроизводимость; ID-seed только для оформления, не реальных орбит/положений |
| K-6 | Сцена в appRef, shared GPU-ресурсы не мутируют; без изменяемых глобальных синглтонов |
| K-7 | Числовые эталоны, unittest, настоящий WebGL/счётчики и визуальная проверка |
| K-8 | Приёмка по пользовательскому сценарию, не числу строк |
| K-9 | Реальные тела на местах выбранной даты; frame/epoch/time/source/accuracy явны |
| K-10 | Итоговый каталог тел/моделей — обновляемая БД; запуск без полного objects.json |

[COORDINATES](docs/COORDINATES.md) — источник семантики; [SOURCE_AUDIT](docs/SOURCE_AUDIT.md) — доказательства источников.
Неизвестность не заменять нулём/ID-фазой/снимком/прежней датой; камера/LOD не двигают центры.

ICRF/SSB/km/TDB, UTC [2000-01-01, 2027-06-28), 100 Horizons-векторов.

JSON→SQLite ограничен по RAM; bounded patches атомарны, публикация пока O(N).

это ограниченные части 3.3/3.4/3.8/3.9, не массовый physical streaming.

1. **Проверено:** минимум реестра 10.0.1 и координат 4.2/4.4/10.5;
   ограниченный менеджер/LOD/бюджеты 3.3/3.4/3.8, диагностика workers/request IDs.

   HTTP → bounded staging SQLite → нормализация/валидация → atomic revision,

   начала, конфликты writers/старые читатели; [приёмка](docs/TEST_COVERAGE.md).
   Граф/индексы/SQLite/legacy остаются O(N); 3.7-B и весь 10.0.1 открыты.
3. **Продуктовая ветка:** ограниченный 6DoF 8.1/минимум 8.2/8.6 принят на пяти
   центрах; реализован opt-in SQLite/HTTP synthetic 100×1000 в том же physical
   manager/renderer/UI: [профиль и приёмка](docs/S100K.md),
   [машинный отчёт](docs/s100k_report.json). Функциональность проверена;
   аппаратные 60+ fps/полный S-100k, весь 8.3/Фаза 8 и массовый streaming открыты.
   Порционный update и отдельные динамические окна реализованы. Текущий
   согласованный пользователем frame p95 ≤16.8ms; прежние16.667ms и результаты
   сохранены как история. Расширенный synthetic stress принят по отчёту;
   monitor presentation и реальный S-100k открыты.
   Затем ограниченное расширение реальных моделей с независимыми векторами.
   Это не ждёт3.7-B/всех источников.
4. **3.7-B:** инкрементальное обновление действующей БД/индексов и ревизий,

   приёмка 3.9/6.1–6.3 на миллионе backend-записей, bounded browser и конкуренции.
5. **Реальные данные:** расширять 10.0.1/10.4/10.3/10.1 по семействам моделей,
   согласуя полную 4.1–4.4/10.5; каждый источник проходит 10.9. Отдельно принять
   реальный S-100k. Массовое подключение требует надёжного импорта/обновлений.
6. **Поверхности и релиз:** 10.2/10.6/10.8 → 8.4; 10.7 → 8.5.
   Фаза 5 независима после физического координатного/ресурсного минимума.
   7/10.9 сопровождают всё; 9.2–9.4 готовить заранее, релиз по 9.1–9.10 и
   пользовательской приёмке 8.7/8.8/10.9/7. Второй backend не строить.

### Приёмка моделей

- [ ] Планеты против JPL Horizons: ≤ 1″ на 1900–2100 (20 дат)
- [ ] Эталонные проверки согласованы по системе отсчёта, эпохе, моменту, шкале времени и типу координат; точность не приписывается данным без основания
- [ ] Луна против Horizons: ≤ 5″; наклон орбиты 5.145°, узлы прецессируют за 18.6 года
- [ ] Долгота центрального меридиана Земли, Марса и Юпитера: ≤ 0.5° на 2026-10-31
- [ ] Венера и Уран вращаются retrograde; наклоны 177.4° и 97.8°
- [ ] Луна синхронна: одна сторона к Земле, либрация по долготе ±7.9°
- [ ] Эксцентриситеты видны: Меркурий 0.206, Плутон 0.249; перигелий в правильную сторону
- [ ] Барицентр Земля–Луна проверен на объявленную дату; ~4 670 км — ориентир
- [ ] Реверс: состояние на одной дате одинаково при подходе из прошлого и будущего; переход на ±100 лет и возврат к исходной дате без дрейфа
- [ ] Фаза Венеры на 2026-10-31 совпадает с Horizons (угол ≤ 1°)
- [ ] Затмение 2027-08-02: тень Луны на Земле в правильной точке
- [ ] Цвет звезды: ΔT ≤ 200 K по B−V для 100 звёзд
- [ ] Чёрные дыры: в согласованной идеализированной модели фотонная сфера
  1.5 r_s, тень 2.6 r_s; доплер-асимметрия отдельно (Фаза 5)
- [ ] Ни одного `Math.random()` в физике (K-5); всё — функции от `simTime`
- [ ] Офлайн: текстуры и коэффициенты эфемерид в образе, без CDN

### Границы физической модели

- N-body, столкновения, приливы, тектоника — для визуального паритета не нужны.
- Отклонение света у лимба Солнца (ориентир 1.75″) вне geometric-контракта;
  при наблюдательном контракте согласовать поправки, не объявлять эффект невидимым.
- Текущий positions/1 — geometric (`corrections=NONE`). Световое время и
  аберрация не объявляются «невидимыми»: для наблюдаемых координат нужен
  отдельный контракт и согласованные поправки/эталоны (LT/LT+S).
- Релятивистские эффекты, кроме чёрных дыр (Фаза 5), — пропускаем.
- Подтверждённые текстуры экзопланет/звёзд из текущих источников не предполагаются.
- Угловые цели задаются для конкретного наблюдателя/дальности и типа координат;
  числовой допуск в km не является абсолютной точностью DE440.
